agentic-devcontainer-feature

All-in-one Local LLM Developer Box — DevContainer Features Collection

GitHub 5 Features 1 Template Multi-Agent HITL Tailscale Ready

Add one features block to any repo and you get a complete local-LLM developer box: a prebuilt CUDA llama-server, on-demand GGUF model fetch, a multi-upstream OpenAI-compatible gateway, and a full multi-agent coding setup with human approval — all wired to a single stack.json manifest and reachable from any device over Tailscale. No cloud APIs required, no baked-in weights: everything runs and downloads locally.

In plain words: this gives you a private, always-on LLM box you can talk to — from your desk or your phone — reachable only over your own Tailscale VPN, and spinning up another one (with different models, or a fresh agent setup) is one features block in any repo.

How to Use

Three ways to engage with this repo — pick the one that fits.

  1. Consumer (new repo) — Add the features block from the Quick Start section below to your devcontainer.json, or apply the llm-lab template.
  2. Self-consumption — This very repo boots the full stack from its own collection: one llama-server per stack.json model (default :8089), bifrost at :8082, opencode agents scaffolded, library books installed (or opt out with WITH_LIBRARY=false), models fetched via fetch-models.sh. A live reference implementation.
  3. Contributor — Read CONTRIBUTING.md for the development workflow, adding new features, and library contributions.

What You Get

Spin up a complete local-LLM developer environment in any repo — a single features block provisions the whole box:

Here's what that adds up to in plain English:

  • It's a private LLM box. llama.cpp serves your models as a standard OpenAI-compatible /v1 API (:8089); the bifrost gateway exposes every loaded model through one endpoint (:8082), so any LLM app or client can use them.
  • Talk to it from your phone. opencode serves a chat UI on :4096 you can open in any browser — from your desk or the train.
  • Private by VPN, not by hiding. On boot the box auto-joins your Tailscale tailnet (node llm-lab via TS_AUTHKEY), so only your own devices can reach it — no public port exposure.
  • New model, no rebuild. Models are declared in stack.json and fetched on-demand at first start; swap or add a model (MODELS or stack.json), or spin up a fresh box with different models, by editing a manifest — never the image.
  • Agent setup in minutes. opencode-agents drops in the CLI, role agents, and the HITL library books; copy the same features block into another repo to recreate the exact setup.

Llama Server

Prebuilt llama.cpp server with CUDA support — OpenAI-compatible /v1 API.

  • Binary at /opt/llama-server/llama-server
  • Symlinked to /usr/local/bin/llama-server
  • Idempotent: NO-OP if already installed (custom image base)
  • Options: VERSION, CUDA_ARCHS, BUNDLE_CUDA_LIBS

Gpu Bridge

WSL2 GPU bridge: symlinks NVIDIA driver libs into the container so CUDA actually works on Windows hosts.

  • Auto-detects WSL2 via /proc/version
  • NO-OP on native Linux
  • Re-verifies /dev/dxg on every start
  • Options: WSL2_ONLY, ENV_REWRITE

Bifrost Gateway

Bifrost gateway exposing llama-servers as OpenAI-compatible providers on :8082.

  • Installs @maximhq/bifrost npm package
  • Materializes config/bifrost.json from stack.json via write-bifrost-config.sh
  • Multi-upstream routing: one provider per model ({name}* wildcard)
  • Options: PORT, VERSION, LLAMA_PORT

On-Demand Models

On-demand GGUF model fetch from HuggingFace — weights are NEVER baked into image layers. Model entries may optionally enable speculative decoding via spec_type: "draft-mtp" / spec_draft_n_max.

  • Installs fetch-models.sh to /usr/local/share/llm-lab/models/
  • Writes the shared stack.json manifest — one entry per served model
  • Idempotent: skip if file already exists
  • Resumable downloads: curl --retry 5 --continue-at -
  • Options: MODELS, ROLES, BIFROST_PORT, MODEL, QUANT, MODELS_DIR

Opencode Agents

Installs the opencode CLI plus the full agentic setup: AGENTS.md, .opencode/agent/*.md, library books, HITL contract.

  • Installs the opencode CLI — opencode on PATH
  • 7 primary agent role definitions
  • Library of reference books with attribution
  • Opt-out: WITH_LIBRARY=false
  • Options: OVERWRITE, WITH_LIBRARY, INSTALL_DIR

Multi-Role Agent Setup

When you use the opencode-agents feature, you get a complete multi-agent workflow with Human-in-the-Loop (HITL) approval — exactly what this repo runs on.

The Agent Roster

  1. Build (orchestrator) — Routes every task through the architect; handles only trivial/operational matters directly. Role: build
  2. Architect — Decomposes every request into discrete, executable subtasks; produces the plan for human approval; delegates to specialists; verifies every claimed artifact exists before reporting success. Role: architect
  3. Coder — Writes and edits code, implements features, fixes bugs, follows existing code style. Role: coder
  4. Researcher — Explores the codebase, searches files/patterns, traces call chains, cites every claim with file:line evidence. Role: researcher
  5. Reviewer — Full audit of every change: correctness, security, style, performance, error handling. No code is complete without reviewer sign-off. Role: reviewer
  6. AI-Researcher — AI-specific research: llama.cpp configs, GGUF quantization, model performance; library-aware. Role: ai-researcher
  7. UI / Artist / 3D-Designer — Interfaces, visual assets, and print-ready geometry as code. Roles: ui, artist, 3d-designer

Human-in-the-Loop (HITL) Workflow

Before any code change is made, this gate is enforced:

  1. Architect plans — breaks the request into discrete subtasks
  2. Human approves — explicit approval required before any code is written
  3. Coder implements — writes code following the approved plan
  4. Reviewer audits — correctness, security, style, performance, error handling
  5. Architect verifies — confirms the changes physically exist on disk before marking complete
HARD GATE — NEVER SKIP STEP 2: no code files may be created, edited, or modified until the human has explicitly approved an architect's plan. Operational tasks (starting services, running commands, reading files) are exempt.

What Consumers Get

  • Complete agent roster — working multi-role delegation (build → architect → specialist → reviewer), not just prompt templates
  • Workspace opencode.json — generated from stack.json by generate-opencode.sh/.jq (one provider per model, role→slot pinning, per-model limit.context); the shipped fragment is the no-manifest fallback (fills empty/{} files, never a real consumer config)
  • HITL enforcement — code changes blocked without explicit human approval; structured approvals via the question tool
  • Anti-stall protocols — atomic delegations, immediate recovery from stuck subagents, bounded iteration, artifact isolation, checkpoint notes
  • Library extensibility — add books via library/<role>/ and register them; the shipped register is never clobbered by re-scaffolds
  • Library opt-out — WITH_LIBRARY=false installs no shipped books; agents stay fully functional
  • Scaled agent communication rules — isolated subagent context, uid-prefixed scratch files, depth awareness (max 2), no recursive delegation

📱 Work From Anywhere with Tailscale

Once the devcontainer boots, your llama-server, bifrost, and opencode endpoints are reachable from your phone over a secure mesh network — no public port exposure required.

Your devcontainer is a devbox you control on the go. Open opencode from your phone — via the OpenCode Mobile Android app (Google Play / F-Droid / APK) or any mobile browser pointed at opencode serve — and you're talking to your full agentic setup: @architect, @coder, @researcher and the rest, wherever you are. Ask for a change, review a diff, kick off a build, or check the llama-server health, all from the palm of your hand, while the heavy compute stays on your box.

1. Start the container

Boot the devcontainer with the features above. llama-server(s) serve on their per-model ports from stack.json (default :8089), bifrost on :8082, opencode serve on :4096.

2. Connect Tailscale

Nothing to run — set TS_AUTHKEY in containerEnv (see Quick Start) and auto-startup runs tailscale up --authkey=… on every container start, joining your tailnet automatically. Running several boxes? Give each a distinct TS_HOSTNAME (default llm-lab) so their tailnet node names never collide.

3. Find your IP

tailscale ip -4

Prints the mesh IP (e.g. 100.x.x.x). This is your always-on address from any device.

4. Open from your phone

Install the Tailscale app on your phone and sign in to the same account. Then either browse straight to your box, or use the dedicated client — OpenCode Mobile, an open-source Android client for opencode (independent, community-built) — point it at http://100.x.x.x:4096 with your server password and run AI coding sessions from your phone over Tailscale:

  • http://100.x.x.x:8089 — llama-server health & API
  • http://100.x.x.x:8082 — bifrost chat UI
  • http://100.x.x.x:4096 — opencode serve (agentic IDE — your devbox remote control)

Use opencode from your phone's browser exactly like on desktop: pick a task, let the agent team plan and implement it on the devbox, and follow along live. It's a full devbox in your pocket — same agents, same library, same models, same repo state.

Zero public exposure. Everything stays inside the Tailscale overlay network — encrypted, authenticated, and only reachable by your own devices. No port forwarding, no cloud tunnel, no firewall holes. Your local LLM lab is a private personal server you carry in your pocket — a full devbox, remote-controlled from your phone.

Full Toolchain — No More command not found

The collection installs the actual binaries the agents use, not just config files. When you add these features, opencode, llama-server, and start-bifrost are real commands on your PATH — the agents call them directly, no manual setup.

  • llama-server — prebuilt llama.cpp binary plus CUDA runtime libs at /usr/local/bin/llama-server; OpenAI-compatible /v1 endpoint per stack.json model (default :8089).
  • Bifrost gateway — bifrost-gateway (v1.1+) provisions its own node/npm runtime when the base image lacks one, then installs @maximhq/bifrost and the start-bifrost launcher.
  • opencode CLI — opencode-agents (v1.1+) installs the official opencode binary, so opencode, opencode serve, and the agent roster all work immediately.
  • Tooling baseline — python3.12, git, curl, sudo, and a shell arrive with the box: everything the multi-agent workflows reference exists in the container.
  • Agent scaffold — AGENTS.md, .opencode/agent/*.md role definitions, and the library/ reference books land in your workspace on first start.
  • Tailscale VPN — the official tailscale/codespace feature installs tailscaled + tailscale; auto-startup joins your tailnet automatically via TS_AUTHKEY (userspace networking, no TUN required).

That's why the sample devcontainer.json below is complete: five features = models, runtime, gateway, agents, and tools — no extra setup steps, no missing binaries.

Reference Examples — Boxes Built on This Collection

The features are the generic part. These four repos are the concrete part — real boxes that consume the collection, and one sibling project that shares the same agentic conventions. Read them to see what a finished setup looks like before building your own.

agentic-code-box

The canonical consumer — the full feature graph wired end to end, and the reference for fitting real models onto a real card.

  • Three GPU profiles (b, d, q) re-quantized and measured on an RTX 5070 (12227 MiB), not guessed
  • Quantized KV (q8_0/q4_0) cuts the coder from 9699 to 5397 MiB — KV, not weights, is the binding constraint
  • bash scripts/use-profile.sh d rewrites the manifest, regenerates stack.json/bifrost.json/opencode.json, and re-fetches only what's missing
  • bash scripts/bench.sh prints VRAM occupancy and throughput per profile
  • No weights in the image — fetched at container-create into the bind-mounted workspace

agentic-redteam

An offensive box. Agents run the round and file every finding as a GitHub issue — but only a human presses the button.

  • bash scripts/run-red.sh drives one round: prep → recon → exploit → report
  • Non-destructive proof-of-concept against a local container asset; the target's app/vulns/INTENT.md defines what is in scope
  • Findings land as separate gh issue create issues labelled security, after human confirmation
  • Explicit scope fence: the local asset and its repo only — host, cloud account, and GitHub itself are out of bounds
  • Carries a DISCLAIMER.md and a human runbook.md for the offensive turns

agentic-blueteam

The other half of the same loop — triaging, fixing, and closing what the red team opened, against the identical asset.

  • bash scripts/run-blue.sh runs: open → triage → mitigate → verify → close-with-proof or reject-with-reason
  • Mitigations land on a issue-N-mitigation branch, never straight on the default
  • Every close requires human approval; every push is gated on the asset's scripts/verify.sh going green
  • Red and blue share one intent contract (INTENT.md), so attacker and defender agree on scope

ailbert sibling

An AI-generated Dilbert-style comic, published weekly at nmwael.github.io/ailbert. Not a consumer of this collection — it's Node, pinned to the cloud model, with no devcontainer or local model. It earns a place here because it runs the same conventions.

  • Self-discovering loop: the writer proposes a gag as panel JSON, the renderer materializes sketchy SVG/PNG, verify_strip.js scores it (weighted to 100, pass ≥ 80), and feedback goes back — ≤ N attempts, then escalate
  • Fully deterministic: the same panel JSON always renders the byte-identical PNG, with committed goldens as a regression set
  • Same AGENTS.md HITL contract and per-role library/ books as this collection
  • assets/manifest.json is the anti-hallucination hard gate — the writer may only reference assets that exist

Read together, the first three show the range: general coding, attacking, and defending. agentic-redteam and agentic-blueteam are the clearest demonstration of the approval gate — the offensive box can assemble a finding but not file it, and the defensive box can prepare a fix but not close it, until a human says so.

Quick Start

Two ways to consume the collection in a new repo:

Template path (recommended)

devcontainer templates apply -w <your-repo> \ -t ghcr.io/nmwael/agentic-devcontainer-feature/llm-lab

Generates .devcontainer/devcontainer.json with GPU_MODE, MODEL (legacy single-model), MODELS/ROLES (JSON multi-upstream), FEATURES_TAG, INCLUDE_AGENTS/INCLUDE_MODELS/INCLUDE_LIBRARY options.

Full example: complete devcontainer.json

Copy this whole file into .devcontainer/devcontainer.json — a one-file, GPU-capable local LLM lab:

{ "name": "local-llm-lab", "image": "nvidia/cuda:13.3.0-cudnn-runtime-ubuntu24.04", "features": { "ghcr.io/nmwael/agentic-devcontainer-feature/llama-server": "1", "ghcr.io/nmwael/agentic-devcontainer-feature/gpu-bridge": "1", "ghcr.io/nmwael/agentic-devcontainer-feature/bifrost-gateway": "1", "ghcr.io/nmwael/agentic-devcontainer-feature/models": "1", "ghcr.io/nmwael/agentic-devcontainer-feature/opencode-agents": "1", "ghcr.io/tailscale/codespace/tailscale": { "version": "latest" } }, "runArgs": [ "--device=nvidia.com/gpu=all", "--shm-size=2g", "--cap-add=SYS_PTRACE", "--security-opt=seccomp:unconfined" ], "forwardPorts": [8082, 8089, 4096], "containerEnv": { "TS_AUTHKEY": "${localEnv:TS_AUTHKEY}" }, "customizations": { "vscode": { "extensions": [ "ms-python.python", "ms-vscode.cpptools" ] } } }

Notes: --device=nvidia.com/gpu=all targets native Linux and WSL2 GPU modes. Set TS_AUTHKEY as a local env var to auto-join your Tailscale tailnet (see Work From Anywhere above); set TS_HOSTNAME to a unique name per box if you run several devcontainers (default llm-lab). The official ghcr.io/tailscale/codespace/tailscale feature adds the VPN; containerEnv: TS_AUTHKEY makes it join automatically on every start. Omit containerEnv/customizations for the minimal lab. For the pre-built vscode user + sudo + python3.12, apply the llm-lab template instead (it ships a Dockerfile variant).
