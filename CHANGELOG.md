# Changelog

All notable changes to this project are documented in this file. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed
- **`opencode-agents` 1.4.0 — blanket `permission: "allow"` in the generator + shipped fragment.** `generate-opencode.jq` emits a top-level `permission: "allow"` in both the cloud and local output object literals, and the shipped `opencode.json.fragment` gains the same top-level key, so scaffolded/generated configs no longer hit permission prompts. The shipped agent `.md` files are unchanged.
- **`models` 1.6.0 — the `ai-researcher` role is removed from the default role maps.** `DEFAULT_ROLES` and `DEFAULT_CLOUD_ROLES` no longer emit an `ai-researcher` entry, so a stock build writes `stack.json` with 7 roles (`architect`, `coder`, `researcher`, `reviewer`, `build`, `ui`, `artist`) instead of 8, and `generate-opencode.jq`/the shipped fragment no longer need a slot-4 pin for it (fragment display name is now `Slot 4 (build/ui/artist)`). The repo's own `.devcontainer/llm-lab-roles.json` and `opencode.json` dropped the same entry. Consumers with an explicit `ROLES`/`.devcontainer/llm-lab-roles.json` mapping may delete their `ai-researcher` key the same way — a leftover entry no longer matches any agent and is simply ignored.
- **`opencode-agents` 1.3.0 — `ai-researcher`/`3d-designer` roles are gone, and every remaining role ships a self-contained instruction file.** The combined `.opencode/agent/agent-roles.md` (one bare multi-role YAML blob with baked `model:` pins) is replaced by six per-role markdown files (`architect`, `coder`, `researcher`, `reviewer`, `ui`, `artist`), each with `description:` + `mode: subagent` frontmatter, **no `model:` key** (slot pinning comes from `opencode.json` generated out of `stack.json`), a short self-contained role contract, and a `## References` section stating that role books, when present, live at `library/<role>/` — `ui`/`artist` reference only `library/EXTENSIONS.md`. The feature no longer ships `library/ai-researcher/` books: the shipped library payload is exactly `skills/` + `release-it.mini.md` + `EXTENSIONS.md`, which `install.sh` now copies and `EXTENSIONS.md` now states. Shipped `AGENTS.md`/`AGENTS_LIFECYCLE.md` repoint the stack pointer at `stack.json` / `.devcontainer/llm-lab-models.json`; `AGENTS.md` also drops the roster rows and 3D-design workflow paragraph (repo-root mirrors stay byte-identical). Repo `library/manifest.json`/`library/README.md` lose the `ai-researcher`/`3d-designer` blocks and `3dprints/` book references, and `docs/index.html`'s roster drops the AI-Researcher bullet.
  - **Consumer note:** `OVERWRITE=true` refreshes never delete files, so a workspace scaffolded before 1.3.0 keeps a stale `.opencode/agent/agent-roles.md` next to the new per-role files — remove it on refresh (`rm .opencode/agent/agent-roles.md`). `scaffold.sh` now deletes it itself right after copying the agent files, so the manual step is only needed when refreshing with an older installed payload.
  - **Delegation contract:** shipped `AGENTS.md` gains `## Orchestration Flow` (user → build → architect → exactly one specialist per atomic subtask → JSON result → architect verifies/synthesizes → re-delegates to the same specialist through the architect only; states the architect-bridge rule, the `subagent_depth` backstop, and the mandatory reviewer gate in one place) and `## Delegation JSON envelope` (field tables + one example directive + one example result). Structured JSON applies to **all** architect ⇄ specialist traffic, with `coder` the strictest case (`artifacts` + `checks` required when `status: done`, `blocker` required otherwise); HITL approval and the architect's user-facing report stay prose + the `question` tool. All six role prompts and `AGENTS_LIFECYCLE.md` (rule 208) point at the contract; repo-root mirrors stay byte-identical and are pinned by new `metadata.bats` checks.

### Fixed
- **`bifrost-gateway` 1.1.4 — the gateway could die silently and nothing supervised it.** A boot instance was observed exiting cleanly ~11 s after its last request — no panic, no OOM kill, it went away right after veth teardown (the container's network interface disappeared) — and supervision was only `auto-startup.sh`'s one-shot start, so every agent request then failed with connection refused until someone re-ran the starter by hand. The feature now ships `bifrost-watchdog.sh` (mode/semantics mirroring `llama-watchdog.sh`): a daemon probes plain `GET /` — the same readiness signal `auto-startup.sh` polls — inside `BIFROST_WATCHDOG_BUDGET` (default 5 s), only acts after one confirming retry, stops the dead or wedged listener before relaunching (kill the `bin.js` launcher for that port, then the `bifrost-http-0` child — a leftover listener would make the starter's curl guard fail and relaunch `EADDRINUSE`), and hands off to the consumer's idempotent `auto-startup.sh`, which reports "already up" instead of double-spawning when the gateway was merely slow. A per-port restart ledger (`BIFROST_WATCHDOG_MAX_RESTARTS`=3, `giving up` once spent, a healthy probe re-arms it) stops a box that cannot boot bifrost from being relaunched every cycle; a `stack.json` with `cloud: true` self-exits (no local gateway to watch); with no restart command resolvable it reports instead of killing, so it can never take the stack down itself. The spawn contract in `auto-startup.sh` is pinned by a new static check — restart hook pointing back at the starter, an **anchored** single-instance guard (an unanchored `pgrep -f bifrost-watchdog` would match a concurrent `--probe`/`--once` whose cmdline ends in the port and skip the spawn), detached `nohup` spawn, and the watchdog install landing before **both** `exit 0` early-exits in `install.sh` (the 1.0.5/1.0.6 lesson: any exit before the install loses it on exactly the base images that need it). `start-bifrost.sh` additionally writes a best-effort `oom_score_adj -100` before `exec node` — `exec` preserves the pid so the write lands on the node wrapper, and `bifrost-http-0` inherits the score at fork, so one write covers both (unprivileged CI containers correctly land on 0; tests assert the direction, never −100). Plus O1: `auto-startup.sh` now **waits** instead of double-spawning when a first boot's 60 s window expires while a launcher is still mid-boot.

### Added
- **`llama-server` 1.0.4 — ships `llama-watchdog.sh`, because `/health` cannot see a server whose generation collapsed.** A degraded llama-server still answers `/health` in milliseconds while decoding at ~0.1 tok/s (observed on both a fresh rebuild and a long-running box after WSL GPU state weirdness: `prompt eval 685 tok/s` on a healthy restart vs `eval time 17587 ms / 4 tokens` when degraded). Every agent turn then burned opencode's 5-minute provider timeout and looked like a hang rather than a dead server, and nothing restarted it because `/health` stayed green. The watchdog probes each model with a 32-token completion (`WATCHDOG_BUDGET`, default 30 s — healthy is ~3 s) and only acts after a confirming retry, skipping the cycle entirely while `/slots` reports `is_processing` so an in-flight generation is never mistaken for degradation. Two failures (or two failed `/health` checks) stop the process and re-run the consumer's idempotent `auto-startup.sh`, which relaunches just the missing server; with no restart command resolvable it reports instead of killing, so it can never take a stack down on its own. Modes: daemon (default, `STACK_JSON` every `WATCHDOG_INTERVAL`=120 s), `--probe PORT [MODEL]`, `--once PORT [MODEL]`.
- **`llama-server` 1.0.5 — the watchdog stops itself from becoming the next loop.** Three hardening guards on top of 1.0.4:
  - **Restart ledger.** `WATCHDOG_MAX_RESTARTS` (default 3) counts consecutive restart attempts per port in `WATCHDOG_STATE` (`/tmp/llama-watchdog.state`); once spent the watchdog reports `giving up` instead of relaunching, and any healthy probe clears that port's count. Without it a box with no weights (agentic-code-box ships profiles but no `.gguf`) or a server that crashes on start would be relaunched every `WATCHDOG_INTERVAL` forever.
  - **`SKIP_LLAMA_START` respected.** The daemon exits cleanly when the consumer skips llama entirely (cloud boxes, GPU-less boxes), before it ever needs `jq` or the manifest.
  - **Cloud manifests skipped.** `stack.json` with `cloud: true` has no local server to watch; the daemon logs and exits instead of probing nothing.
  - **Bare invocation actually reaches the daemon.** In 1.0.4 the argument parser routed *no arguments* to `--help`, so the spawn line in `auto-startup.sh` (`sh llama-watchdog`, no args) printed usage and exited 0 — the watchdog never watched anything. `-h`/`--help` now show usage, no args runs the daemon, and a bats test asserts the bare path reaches the manifest guards (exit 1 without a manifest) instead of stopping at help.

### Fixed
- **`llama-server` 1.0.6 — the watchdog never got installed on a rebuild, so the box silently fell back to the repo copy.** `install.sh` placed the `llama-watchdog.sh` copy *after* the idempotence early-exit (`[ -f /opt/llama-server/llama-server ]` → `exit 0`). A rebuild is exactly that case: the binary rides in from the base image / a cached layer (`COPY --from=llamacpp`), so install.sh took the early-exit and 1.0.5's watchdog never landed — verified on a fresh `devcontainer up` of capability-testing, where feature metadata reported `llama-server:1.0.5` while `/usr/local/bin/llama-watchdog` was absent and `auto-startup.sh` had to spawn `scripts/llama-watchdog.sh` from the workspace. The install block now runs before the early-exit (with `mkdir -p "$INSTALL_PATH"` for a pre-seeded directory), a static test asserts the ordering, and the version bump also busts the buildkit cache that had frozen the no-watchdog layer.

### Fixed
- **`opencode-agents` 1.2.3 — `limit.output` equalled `limit.context`, which drove opencode into an infinite compact loop.** opencode compacts the conversation when `tokens (input + output + cache read + cache write) >= limit.context - min(20000, maxOutputTokens)`. The generator emitted `output: ($m.output // $m.context)`, so that threshold was `context - context = 0` and **every** assistant turn was followed by a `compaction` turn — forever. Seen in capability-testing profile `q`: the 8b orchestrator session compacted 7× in 3.5 minutes, a coder session 18× in 5 minutes (`agent=compaction` alternating with the agent turn, ending in `compaction in=0 out=0`), and generations ballooned to 4-5k tokens because the provider was told it could emit up to `limit.output`. `generate-opencode.jq` and the shipped `opencode.json.fragment` (which had `output: 65536`) now default `output` to **8192**: threshold becomes `context - 8192` (32768 for a 40960 model) and the per-turn output cap is sane. An explicit per-model `output` in a profile still wins (`$m.output`), and flows through `stack.json` untouched because `llm_write_stack` copies the profile array verbatim.

### Fixed
- **`bifrost-gateway` 1.1.3 — the gateway's upstreams were unreachable: every chat request 404'd and model resolution failed.** Two root causes in `write-bifrost-config.sh`:
  - **Doubled `/v1` path.** `network_config.base_url` was `http://127.0.0.1:{port}/v1`, but bifrost appends `/v1/chat/completions` to `base_url` itself when `base_provider_type` is `openai`. The upstream request became `http://127.0.0.1:8089/v1/v1/chat/completions` and llama-server returned `404` (verified with an HTTP path logger: bifrost sent `POST /v1/v1/chat/completions`). `base_url` is now `http://127.0.0.1:{port}` — no `/v1`.
  - **Wildcard allowlist never matched.** `keys[].models` was `["{name}*"]`, but bifrost v2.2.6 matches allowlist entries **exactly** — a request for `qwen3-8b-s0` does not match the entry `qwen3-8b*` — so resolution failed with `could not auto resolve a provider for the request`. The only wildcard bifrost honours is the whole-string catch-all `["*"]`, and on multi-provider configs that misroutes (with two providers it sent `qwen3-8b` to the `qwen2.5-coder-7b` upstream). The generator now emits the exact ids clients request: `{name}` plus `{name}-s{slot}` for every slot below the model's `parallel` count (`parallel` defaulting to 1). The legacy single-upstream fallback keeps `["*"]` (single provider, catch-all is correct there).

### Fixed
- **`bifrost-gateway` 1.1.2 — the gateway never listened on `PORT`, and never loaded the generated config.** Two independent bugs, both of which made the gateway look "down" (process alive, nothing reachable) and both pre-existing:
  - **Wrong port.** The launcher ran `node bin.js "$PORT_ENV"`, but bifrost v2.2.x parses the port as a **`-port` flag**, not a positional argument. The positional value was silently discarded, so the server started on its own built-in default `127.0.0.1:8080` and `BIFROST_PORT`/`PORT` (default `8082`) was unreachable — `auto-startup.sh` waited on `:8082`, the health probe failed, and the gateway appeared down even though the process was running. `-host` also defaults to `localhost` only, so it was unreachable off-box too. The launcher now passes `-port "$PORT_ENV" -host "$HOST_ENV"` (default host `0.0.0.0`, overridable via `BIFROST_HOST`).
  - **Config never read.** `write-bifrost-config.sh` materializes `<BIFROST_DIR>/config/bifrost.json`, but bifrost reads `<app-dir>/config.json` (default app-dir `/root/.config/bifrost`). Bifrost therefore logged `config file not found ... initializing with default values` and started with **zero providers**, so every request failed with `could not auto resolve a provider` and `/v1/models` returned `{"data":[]}`. The launcher now syncs the generated config into bifrost's app-dir on start (overridable via `BIFROST_APP_DIR`), which keeps routing correct even when the config is refreshed after the build stage (runtime `resolve-stack.sh`).

  Three new regression tests guard these: a static assertion that the flag form is used and the positional form is absent, a static assertion that the app-dir sync is present, and an end-to-end check that `BIFROST_PORT` actually binds.

### Fixed
- **`models` 1.4.0 — profile files and `models_dir` are resolved at RUNTIME, not build time.** A feature installs during the build stage, but the repo is bind-mounted at container start, so `install.sh` could never read `.devcontainer/llm-lab-models.json`. Compounding it, the `$PWD/models` default baked the CLI's temp feature-extraction path into `stack.json` and `/etc/environment` (e.g. `/tmp/dev-container-features/models_3/models`), leaving a working box unable to find any weights:
  - **New `resolve-stack.sh`** — wired via the feature's `postCreateCommand` (the CLI runs lifecycle hooks with cwd = the workspace folder). Reads `.devcontainer/llm-lab-{models,roles}.json`, applies the same integrity validation as the build, and rewrites `stack.json`, the `models.json` mirror, and the bifrost routing config.
  - **`MODELS_DIR`** — no longer defaults to `$PWD/models`. Empty at build time; the resolver sets it to `<workspace>/models` unless explicitly configured. `/etc/environment` is only written when `MODELS_DIR` is set, so no stale/empty export can shadow the runtime value.
  - **New `stack-lib.sh`** — shared validators/writers sourced by both `install.sh` and `resolve-stack.sh`, so the two paths cannot drift.
  - **Explicit options win.** `install.sh` records whether `MODELS`/`ROLES` arrived as feature options (`/usr/local/share/llm-lab/.build-state`); when they did, the resolver leaves the stack untouched instead of clobbering it with a workspace profile file.
  - Switching profiles now needs only a container restart, not a rebuild. The resolver is idempotent and rejects malformed JSON, unknown role models, and slots beyond a model's `parallel` count without corrupting a working stack.
  - **Tests** — `test/models/runtime-resolution.sh` (14 assertions, runs inside `devcontainer features test`) covers the build/runtime split, precedence, cloud-mode preservation, idempotency, and the integrity rejections. The old `test.sh` assertion that `MODELS_DIR` was always exported to `/etc/environment` now asserts the opposite (no stale build-time export).
- **`models` 1.5.0 — optional per-model speculative-decoding fields (`spec_type: "draft-mtp"`, `spec_draft_n_max`), validated in `llm_validate_local`, passed through to `stack.json`, and emitted as `--spec-type draft-mtp [--spec-draft-n-max N]` by instance launchers.
